# Doc Target Matching Rules

## Auto-Detection

When no explicit doc list provided, scan repo root and common locations for:
1. `CLAUDE.md` — project spec / build instructions
2. Nested `CLAUDE.md` files — `**/CLAUDE.md` anywhere below the repo root (e.g. `src/app/CLAUDE.md`, `src/lib/supabase/CLAUDE.md`). Each applies to its subtree.
3. `AGENTS.md` — Codex / multi-agent companion file. Same treatment as CLAUDE.md.
4. `README.md` — public-facing project documentation
5. `docs/**/*.md` — human-facing reference documentation. **Exclude** `docs/spec/**`, `docs/archive/**`, and any file under a directory whose name starts with `.` — those are frozen by design.
6. `MEMORY.md` or `.claude/**/MEMORY.md` — agent memory files
7. `.env.example` — environment variable template
8. `CHANGELOG.md` — project change history

Only target files that actually exist (except CHANGELOG.md, which gets created if missing).

### Exclusions

Never sync or flag drift in these paths — they are intentionally frozen or generated:
- `.planning/**` — GSD planning artifacts (append-only)
- `.context/**` — historical snapshots
- `docs/spec/**`, `docs/archive/**`
- `node_modules/**`, `.next/**`, `dist/**`, `build/**`
- Any block between `<!-- gitnexus:start -->` and `<!-- gitnexus:end -->` (auto-regenerated by GitNexus)

## Section Detection

### Markdown Heading Hierarchy

Parse headings to build a section tree. Match by heading text content, case-insensitive:

```
## Environment Variables    → env var tables
## Config / Configuration   → config tables
## File Structure           → directory trees
## Dependencies             → dependency tables
## Security                 → security requirements
## Build Phases / Status    → phase tracking
## What's Built / Features  → feature lists
```

### Markdown Table Detection

Tables start with `| Header |` rows followed by `| --- |` separator rows. Match tables by:
1. **Column headers**: Look for columns named Variable, Name, Default, Value, Required, Status, Phase
2. **Proximity to headings**: A table under "## Environment Variables" is an env var table
3. **Content patterns**: Rows containing `SCREAMING_CASE` values are likely env var tables

### CLAUDE.md Patterns

| Change Type | Target Section(s) |
|-------------|-------------------|
| `env_var` | H3 "Environment Variables" tables (Current / Planned) |
| `config` | H3 "Environment Variables", H2 "Security Requirements" |
| `new_file` | H3 "File Structure" code blocks |
| `dependency` | H3 "Dependencies" table |
| `test_count` | H3 "What's Already Built" prose mentioning "N tests" |
| `phase_status` | H2 "Build Phases" table |
| `security` | H2 "Security Requirements" tables |

### README.md Patterns

| Change Type | Target Section(s) |
|-------------|-------------------|
| `env_var` | Configuration / Setup sections with tables |
| `config` | Configuration / Setup sections |
| `new_file` | Project Structure code blocks |
| `dependency` | Installation / Dependencies sections |
| `test_count` | Badges or "N tests" mentions |
| `phase_status` | Features / Status sections |
| `breaking` | Migration / Upgrading / Breaking Changes sections |

### MEMORY.md Patterns

MEMORY.md uses `## Heading` sections with bullet-point notes:
```
## Architecture
- Key point about architecture

## Key Patterns
- **pattern name:** description
```

| Change Type | Target Section(s) |
|-------------|-------------------|
| `env_var` | "Key Patterns" or "Architecture" sections |
| `function_sig` | Section containing function's module (e.g., "Voice Pipeline Notes") |
| `new_file` | "Architecture" section |
| `phase_status` | "Phase Status" section |
| `config` | "Key Patterns" section |

### .env.example Patterns

Format: comment blocks followed by variable lines:
```
# Description of variable
# Optional additional context
VARIABLE_NAME=default_value
```

Group new variables near related existing ones. Match by prefix (e.g., `THINKING_` near other thinking-related vars, `OPENAI_` near other OpenAI vars).

### CHANGELOG.md Patterns

Uses Keep a Changelog format. Target the `## [Unreleased]` section. See `rules/changelog.md` for details.

## Test Count Detection

When test changes are detected, run the test command from `package.json` `scripts.test` to get the actual count:
```bash
npm test 2>&1 | tail -5
```

If `scripts.test` is not defined, try common runners in order: `npx vitest run`, `npx jest`, `npx mocha`. Use whichever is present in `devDependencies`.

## Matching Priority

When a change maps to multiple sections in the same file, update all of them. When a section doesn't exist but should, note it as a gap but don't create new sections — flag for user decision.
